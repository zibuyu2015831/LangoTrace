# 任务方案：标题

状态：Draft
自审核状态：Not Reviewed
类型：feature / bug / refactor / research / chore / docs
创建日期：YYYY-MM-DD
最后更新日期：YYYY-MM-DD

## 用户确认记录

状态为 `Draft` 时不能开始实现。用户确认后记录确认时间、确认内容和范围边界。

## 1. 需求或 bug 描述

说明用户要解决的问题、要实现的能力，或 bug 的可观察现象。

## 2. 现状描述

说明当前代码、文档、产品状态和已知限制。

## 3. 目标

列出本任务完成后必须达到的结果。

## 4. 范围

列出本任务会修改或检查的范围。

## 5. 不做什么

明确排除项，避免任务膨胀。

## 6. 证据与决策依据

列出代码证据、文档证据、用户确认、ADR、spec 或参考实现。

如任务属于 AI Provider、TTS Provider、数据迁移、平台页面或 Prompt 等高风险动作，应引用对应 `docs/workflows/` 手册，并说明采纳或偏离原因。

参考研究、外部项目或重大文档治理结论被采纳前，应写清：

```text
证据能证明什么：
证据不能证明什么：
迁移前提：
照搬风险：
```

高风险或研究性任务补充：

```text
是否需要 spike / probe / fixture / evidence：
需要时的落点：
是否包含真实用户敏感内容：
如何验证和清理：
```

来源于 review round、health ledger 或运行期诊断时补充"审计发现与 work item 对照"：

```text
来源：round id / health-ledger trigger / runtime trigger
发现 ID 或 trigger ID：
严重度：
对应 work item：
验证证据：
```

## 7. 约束映射与验证路径

列出本任务命中的开发约束，指向原始权威文档；不命中任何约束时写"无特殊约束"。

可参考 `docs/_meta/documentation-constraints.md` 快速定位相关约束来源。每条约束只记录已有 LangoTrace 权威文档来源的规则；不把外部参考或 AI 推断升级为 blocker。

```text
### 约束 1：<短标题>

- 约束 ID：DOC-CONST-XXX（如适用）
- 来源：<文档路径，可写到章节或标题>
- 适用范围：<全局 / 模块 / 平台 / 文档域>
- 严重度：blocker / warn / info
- 执行或验证方式：<单元测试 / 脚本 / 人工审查 / 专项 review / 不适用>
- 验证提示：<后续实施者如何确认该约束被满足>
- 说明：<为什么这条约束属于本任务；没有补充说明时写"无">
```

如果任务包含多条约束，可在段落块之前增加短摘要表，但摘要表不替代段落块；长文本、路径和验证提示以段落块为准。

## 8. 涉及的代码文件路径

列出预计修改的代码文件；文档-only 任务写"无"。

## 9. 参考的代码文件路径

列出只读参考文件；没有则写"无"。

## 10. 涉及的文档路径

列出预计修改、参考或需要同步检查的文档。

## 11. bug 分析

仅 bug 任务必填：

```text
复现方式：
预期行为：
实际行为：
根因分析：
置信度：0% - 100%
置信度依据：
备选原因：
回归测试方案：
```

非 bug 任务写"非 bug 任务，不适用"。

## 12. 实施方案

写清步骤、文件、顺序和关键边界。

高风险、多阶段、跨 package 或超过 3 个阶段的任务，可增加 Phase 0 spike / baseline gate：

```text
假设名称：
probe / fixture / baseline 路径：
PASS 条件：
FAIL 条件：
FAIL 后处理方式：
是否允许进入生产实现：
```

## 13. 严格方案自审核记录

按 `docs/plans/plan-review-protocol.md` 在进入实现前填写。低风险例外或用户明确跳过时，也要写明原因和剩余风险。

自审核发现的问题必须先修订并写回本方案。修订完成后，才可以将文档头部的 `自审核状态` 从 `Not Reviewed` 改为 `Reviewed`。

```text
审核日期：
审核方式：隔离审查 / 主会话自审核
审核轮次：第一轮 / 第二轮 / 单轮
未使用隔离审查的原因：
发现摘要：
写回修改：
仍需用户确认的问题：
是否允许进入实现：
```

## 14. 复查方法

说明如何从代码、文档和行为上复查结果。

高风险能力应检查故障与恢复路径，例如失败、取消、超时、Keychain 缺失、migration 失败、Provider 不支持、结构化输出不合法或平台承载不可用。

## 15. TDD / 测试落点

本章节回答"写哪个测试、写在哪里、第一个失败用例是什么"，与第 16 节"验证命令"（回答"运行什么命令"）不重叠。

如果任务涉及新功能、bug 修复、架构调整或行为变化，必须填写本节；如果不新增单元测试，必须说明原因并在第 20 节记录剩余风险。

```text
测试落点：<Package 路径 + 测试文件路径 + 测试类名>
先失败用例：<第一个应先失败的测试函数名 + 预期失败原因>
聚焦验证命令：<swift test --package-path Packages/<target> --filter <TestName>>
不新增单元测试的原因（如适用）：<文档-only / 纯视觉文案 / 无法自动化的手动验证 / 其他>
```

文档-only 任务写"文档-only 任务，行为变化无法用单元测试覆盖，验证依赖第 16 节文档命令"。

## 16. 验证命令

列出完成前必须运行的命令。聚焦命令用于快速红绿验证，完整命令用于收口前最终确认。

大型多阶段任务可增加阶段 DoD 检查命令；这些命令只检查结构性事实，不替代语义审查：

```bash
# Phase 0 DoD

# Phase 1 DoD
```

## 17. 文档影响检查

说明是否影响入口、ADR、spec、architecture、testing、release、review 或其他长期文档。

## 18. 实施记录

按时间记录实际改动、偏离方案的原因、验证结果和提交信息。

如实施中出现 deferred / aborted 项，记录延后 / 中止决策日志：

```text
项目：
决策类型：deferred / aborted
原因：
影响：
后续事实源或复审入口：
```

## 19. 完成标准

列出任务可以从 `active/` 移入 `done/` 的条件。

高风险任务移入 `done/` 前，应补充 plan-vs-shipped 对账：

```text
work item 是否都有文档 / 代码 / 测试 / 脚本 / review evidence：
scope-down 是否已记录：
deferred / aborted 项是否已从完成叙事中剥离：
后续事实源或复审入口：
```

## 20. 剩余风险

列出未解决风险、未覆盖验证或后续任务。
