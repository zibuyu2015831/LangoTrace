# 任务方案：标题

状态：Draft
类型：feature / bug / refactor / research / chore / docs
创建日期：YYYY-MM-DD
最后更新日期：YYYY-MM-DD

## 用户确认记录

状态为 `Draft` 时不能开始实现。用户确认后记录确认时间、确认内容和范围边界。

## 1. 需求或 bug 描述

说明用户要解决的问题、要实现的能力，或 bug 的可观察现象。

## 2. 现状描述

说明当前代码、文档、产品状态和已知限制。

## 3. 目标

列出本任务完成后必须达到的结果。

## 4. 范围

列出本任务会修改或检查的范围。

## 5. 不做什么

明确排除项，避免任务膨胀。

## 6. 证据与决策依据

列出代码证据、文档证据、用户确认、ADR、spec 或参考实现。

如任务属于 AI Provider、TTS Provider、数据迁移、平台页面或 Prompt 等高风险动作，应引用对应 `docs/workflows/` 手册，并说明采纳或偏离原因。

## 7. 涉及的代码文件路径

列出预计修改的代码文件；文档-only 任务写“无”。

## 8. 参考的代码文件路径

列出只读参考文件；没有则写“无”。

## 9. 涉及的文档路径

列出预计修改、参考或需要同步检查的文档。

## 10. bug 分析

仅 bug 任务必填：

```text
复现方式：
预期行为：
实际行为：
根因分析：
置信度：0% - 100%
置信度依据：
备选原因：
回归测试方案：
```

非 bug 任务写“非 bug 任务，不适用”。

## 11. 实施方案

写清步骤、文件、顺序和关键边界。

## 12. 复查方法

说明如何从代码、文档和行为上复查结果。

高风险能力应检查故障与恢复路径，例如失败、取消、超时、Keychain 缺失、migration 失败、Provider 不支持、结构化输出不合法或平台承载不可用。

## 13. 验证命令

列出完成前必须运行的命令。

## 14. 文档影响检查

说明是否影响入口、ADR、spec、architecture、testing、release、review 或其他长期文档。

## 15. 实施记录

按时间记录实际改动、偏离方案的原因、验证结果和提交信息。

## 16. 完成标准

列出任务可以从 `active/` 移入 `done/` 的条件。

## 17. 剩余风险

列出未解决风险、未覆盖验证或后续任务。
