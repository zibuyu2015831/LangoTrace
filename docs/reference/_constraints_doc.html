constraints 系统说明 — code_agent_pro

从 blueprint Pass 0/1/2 + arch.json 派生出来的 12 类 constraint。 本文档说明每类的派生来源、字段、严重程度、enforced_by、消费位置， 外加 rb_nlsh / rb_arborparser / rb_hex 三个 case 的实际数量分布。

① Pipeline 数据流
arch.json + Pass 0 intent + Pass 1 decisions + Pass 2 structure │ ▼ project_constraints.py:project() │ ▼ (deterministic) constraints.json │ ┌────────────┼────────────┐ ▼ ▼ ▼ module_spec codegen audit (post) (intent/ (variant (POST-blueprint conventions strategies + runtime + arch slice; when checks) constraints ambiguity 是 FYI 不强制) flagged)
①.5 为什么这套分类有效 — 4 个正交轴

每条 constraint 由 4 个互不相关的属性唯一定位。如果两个 kind 在 4 个轴上取值完全一样，它们就冗余应合并； 如果某 kind 在某轴取值跟其他 kind 都不同，它就有独立存在的理由。

轴取值区分什么
POLARITYNOT-do · MUST-do · STRUCTURAL · MAY-choose这条规则是禁止 / 要求 / 关系 / 选择
SOURCEintent · decisions · structure · arch从蓝图哪个字段派生 (反向溯源能力)
ENFORCED_BYcodegen-prompt · static-check · test · runtime-assert · variant-trigger用什么机制验证
SCOPEglobal / per-module / per-class应用范围
①.6 12 个 kind 分成 5 个 family
A 负向规则 (2 kinds)
什么不能做 — 违反 = 多产出了不该有的功能/写法
  • hard_dont ← intent.non_goals (feature-level)
  • forbidden_pattern ← conventions.forbidden (pattern-level)
B 正向目标 (4 kinds)
必须满足什么 — 违反 = 漏功能/漏鲁棒性
  • quality_target ← intent.NFRs (with metric)
  • signature_default ← arch shape (mutable attr 无默认)
  • method_kind ← arch operations (factory-prefix heuristic)
  • validation_required ← intent.FRs/NFRs (keyword 'validate'/'raise on')
C 结构关系 (5 kinds)
组件间必须遵守什么关系 — 验证靠 import 图 / 调用图 / 时序
  • dependency_rule ← architecture.dependency_rule + topology
  • concurrency_rule ← execution_model + concurrency_boundaries
  • error_contract ← error_model + error_routing
  • cross_cutting ← io_boundary + cross_cutting.{validation,auth,…}
  • resource_lifecycle ← resource_lifecycles[]
D 数据不变式 (1 kind)
数据字段间/状态机间的关系 — runtime assert + test (★ 当前有 over-derive 风险)
  • data_invariant ← datastructures.invariants + state_machines.guards
E 变体触发器 (3 kinds)
arch underspec → 让 codegen scatter K 个实现
  • protected_param_pair ← arch (_X + X 并存检测)
  • ambiguity_point ← arch (无 __init__ + ≥2 mutable attrs)
  • literal_undefined ← arch (isFinal=true + value 缺失)
总计：5 families / 12 kinds

每行的 4-tuple 都唯一,没有冗余项。 hard_dont vs forbidden_pattern 的区别在 source (feature-level vs pattern-level)； concurrency_rule vs dependency_rule 看似都是模块间关系，但 ENFORCED_BY 完全不同 (运行时断言 vs 静态导入图)。

①.8 这套分类为什么"有效"的 4 条证据
✅ 每条 constraint 一个明确的 enforcement 路径
不同 kind 用不同的 verification 工具：signature_default 用 ast.parse；dependency_rule 用 import graph；data_invariant 用 runtime assert。audit 阶段根据 kind 路由到对应 checker。
✅ 每条 constraint 有反向溯源
给定 kind + source 字段，能精准回到蓝图哪段文字派生它。debugging 失败时能定位是 Pass 0 / Pass 1 / arch detection 哪一步判错了。
✅ 正交轴让 LLM 看 prompt 时易区分
"你必须" (B) / "你不能" (A) / "X 在 Y 之前" (C) 在 prompt 里语气不同；data_invariant (D) 是断言不是规则；variant trigger (E) 不进 codegen prompt，进的是 driver 调度决策。
✅ 5 family 对应 5 种 enforcement 风格 → 消费链路天然分流
A → codegen prompt 禁用语；B → codegen + test；C → 静态/运行时验证；D → runtime assert + test；E → driver 多变体调度。

⑥ 一句话总结

15 个 kind 不是凑的 —— 它们在 (polarity × source × enforcement × scope) 四维空间里 每个都占据一个独特格子，且每个格子对应一种不同的 enforcement 工具/消费者， 所以分类有效。最终结构： 5 family / 15 kinds — A 负向 (2) · B 正向 (4 含 method_kind / validation_required) · C 结构关系 (5) · D 数据不变式 (1) · E 变体触发 (3 含 literal_undefined)。
