# 工作记录：标题

类型：feature / bug / refactor / research / chore

状态：Draft

日期：YYYY-MM-DD

关联文档：

- `docs/README.md`

关联 ADR：

- 无

关联提交：

- 未提交

## 1. 背景

说明这次工作从哪里来。功能任务说明用户需求和产品价值；bug 任务说明现象和影响；重构或调研任务说明触发原因。

## 2. 目标

说明这次工作要达到什么结果。目标应可验证，不写空泛愿望。

## 3. 范围

列出本次会处理的内容。

## 4. 不做什么

明确本次不处理的内容，避免范围蔓延。

## 5. 分析

记录对产品、交互、技术、数据、隐私、同步、权限、测试或发布的影响分析。

bug 任务应在这里记录：

- 复现步骤。
- 期望行为。
- 实际行为。
- 初步根因判断。

## 6. 方案

说明准备采用的方案、替代方案和取舍理由。

## 7. 风险与边界

记录潜在风险、回滚方式、兼容性、数据安全、隐私边界和跨端影响。

## 8. 测试与验证

列出完成前要运行的命令、手动验证步骤和预期结果。

## 9. 文档影响检查

记录本次变更是否影响 `docs/README.md`、主参考文档、架构文档、guidelines、testing、release 或 `docs/review/`。

如果命中 `docs/review/README.md` 中的专项审查触发条件，应记录对应审查轮次；如果跳过专项审查，应说明原因。

## 10. 用户确认记录

状态为 `Draft` 时不能开始实现。

用户确认后记录：

```text
YYYY-MM-DD：用户确认本方案，可以开始实现。
```

## 11. 实施记录

实现后记录实际改动、关键文件、偏离原方案的地方和原因。

## 12. 验证结果

记录实际执行的验证命令、结果和剩余风险。
