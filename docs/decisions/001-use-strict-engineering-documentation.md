# ADR-001: 从项目初始化阶段采用严格工程化文档体系

日期：2026-05-17

状态：Accepted

## 背景

语迹 LangoTrace 目标是开发一款面向付费用户、长期使用、支持 iPhone、iPad 和 macOS 的语言学习 App。产品涉及日记、照片、语音、AI 请求、TTS、OCR、同步、买断制付费、长期本地数据和隐私边界。

如果早期只依赖聊天记录或临时笔记，后续很容易出现以下问题：

- 关键产品判断无法回溯。
- 技术取舍缺少依据。
- 数据、同步、隐私和发布风险被推迟到后期。
- 新会话或后续开发无法快速理解项目状态。
- 付费 App 所需的稳定性和可维护性被早期快速原型侵蚀。

## 决策

从项目初始化阶段开始采用严格工程化文档体系。

具体要求：

- `docs/README.md` 作为文档总入口。
- `docs/_meta/documentation-system.md` 规定文档分层、更新规则和提交前检查。
- 重要架构和产品取舍进入 `docs/decisions/`。
- 架构边界进入 `docs/architecture/`。
- 阶段级 runbook、工程初始化记录和跨任务工程路线进入 `docs/development/`。
- 测试策略和验证记录进入 `docs/testing/`。
- 发布、StoreKit、隐私标签和审核事项进入 `docs/release/`。
- 新功能、bug 修复、架构调整和高风险任务先写 `docs/plans/active/` 任务方案。
- 开发一致性规范和模块级实现地图进入 `docs/spec/`；`docs/decisions/` 不维护 implementation 文档。

## 备选方案

### 方案 A：轻量文档

只保留产品主文档、技术路线和开发环境记录。

优点：

- 维护成本低。
- 早期推进速度快。

缺点：

- 不适合长期付费 App。
- 后续架构、测试、隐私和发布事项容易散落。
- 关键决策缺少稳定回溯入口。

### 方案 B：严格工程化文档

从早期建立主参考、架构、决策、开发、测试、发布和研究文档分层。

优点：

- 决策可回溯。
- 风险能早期暴露。
- 更适合长期维护和后续多人协作。
- 符合付费 App 对稳定性、隐私和发布质量的要求。

缺点：

- 初期文档维护成本更高。
- 需要避免为了文档而文档。

## 影响

- 后续重大变更不能只停留在聊天中，必须写回对应文档。
- 涉及数据、同步、隐私、AI 请求、StoreKit 和发布的能力，需要在进入实现前明确边界和验证方式。
- 文档体系本身也需要随项目阶段演进，但变更应保留记录。

## 风险

- 文档过多可能降低推进速度。
- 如果文档没有和实现同步，会形成误导。
- 如果所有小修改都要求完整规格，会产生不必要负担。

缓解方式：

- 只有重大功能、架构取舍、数据边界、隐私边界、付费发布相关内容必须写入长期文档。
- 小型阶段记录可以放入 `docs/development/` 或 `docs/testing/`，但不能替代单项任务方案。
- 每次提交前检查文档与实际状态是否一致。

## 复审条件

以下情况需要复审本决策：

- 项目从单人开发转为多人团队协作。
- 项目范围明显缩小为内部 Demo 或一次性原型。
- 文档维护成本明显阻碍核心开发。
- 进入 TestFlight 或 App Store 发布前，需要进一步收紧发布与测试文档要求。
