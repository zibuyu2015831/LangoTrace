## 1. 一句话定位

> 语伴是语迹内置的、**默认关闭、需用户手动开启**的「扎根于个人生活记录的目标语言对话练习」功能：一个始终用当前语言空间目标语言、像真人一样聊天的语言伙伴；它不是通用 AI 助手，而是补齐「自由产出（自己用目标语言互动表达）」这一练习模态。

## 2. 已确认的关键决策（2026-06-13 用户拍板）

### 第 1 轮
1. **允许修改产品定位**。理由：AI 对话几乎是主流 AI 语言学习工具的基础能力，缺失会削弱竞争力。但语迹仍坚持把语伴**严格约束为「扎根记录的语言对话练习模态」**，而非通用聊天助手。该定位变更**必须新增 / 更新 ADR**（见 §6）。
2. **语伴必须是可控开关**：用户在系统设置中决定是否开启；关闭时菜单 / 导航不出现该项，相关数据路径不激活。
3. **隐私「找话题」方案 A 与方案 B 兼容实现**（详见 §3.6）。
4. **时机暂时搁置**：先不进入实现，也暂不强行插入现有 15 本方案系列；本文件仅做需求留存。

### 第 2 轮
5. **开关默认关闭**，必须用户手动开启。
6. **会话历史可删除，且有两种粒度**：
   - 「删除某条」= 删除该条**及其之后的全部消息**（保证线性上下文自洽，见 §3.2 设计理由）。
   - 「清空 / 重新开始」= 删除整段会话历史。
7. **用户不能直接设定 system prompt**；但可指定 AI **语气、风格等简要信息**，由系统嵌入提示词。用户可设置的部分**优先用选项（枚举）而非自由文本输入**，避免输入错误或注入损坏提示词（见 §3.3、§6.6）。
8. **AI 默认不主动纠错**；但当用户输入错误过多、影响理解时，应**模拟真人**进行确认 / 二次询问，或给出调侃、玩笑等自然回应（见 §3.4）。
9. **回复要求文本流式输出**；若基础设施未就绪，**可推迟到基础设施完善后再实施**（见 §5.2、§7）。
10. **语种识别优先本地**；若本地效果不佳，**回退为由 AI 在请求时自行判定**——在系统提示词中写入用户当前目标语言与源语言，并做好「遇目标语言则…、遇源语言则…」的路由分发（见 §3.5）。
11. **聊天内容支持词汇 / 表达提取到记忆库**等学习沉淀功能，与记忆系统打通（见 §3.8）。

## 3. 功能点详述

### 3.1 开关与入口
- 设置中新增「语伴」开关，**默认关闭**，需用户手动开启。
- 开启后在三端导航 / 菜单栏新增「语伴」入口；关闭则隐藏入口且不激活数据与 AI 路径。

### 3.2 会话形态与历史管理
- **始终只有一个会话**，不支持新建 / 多会话管理；定位为「一个固定的对话对象」。
- **删除某条消息**：删除该条**及其后续全部消息**。
  - 设计理由：单一会话本质是**线性上下文链**，删中间、留后面会造成上下文断裂与 AI 行为错乱；「从该条往后删」是唯一自洽的模型。
  - 实现提示：若启用「滚动摘要 / 对话记忆」，删除点之后的摘要必须**一并失效并重建**，否则被删内容会残留在摘要里继续影响回复。**（LM03-S3b-1 已落地：删该条及后续 / 清空在同一 write 事务内按水位失效重建，重建惰性，见 `plans/done/2026-06-26-feature-lm03-s3b1-companion-rolling-summary.md`）**
- **清空 / 重新开始**：删除整段会话历史（含摘要），回到空白会话。两类删除都只作用于**本地历史**，符合可删除原则。
- 设计为**真人聊天体感**：自然、连续、有人设；人设由 Prompt Registry 固定模板 + 用户选项拼装（见 §3.3）。
- **按语言空间隔离**：每个语言空间有各自独立的语伴会话、人设与历史（目标语言、话题、关系记忆都不同）；切换空间即切换语伴，历史互不串扰。这是一项需在实现前确认的架构边界，会话表应带 language space 外键。
- **编辑自己刚发的消息**（若提供）：因同样涉及线性上下文，编辑等价于「从该条起删除并重发」，语义与上面的删除规则一致。

### 3.3 人设、语气与风格（选项化，防注入）
- 用户**不能编写或看到 system prompt**。
- 用户可通过**有限选项（枚举）**调节语气、风格等简要偏好（语气 = 友好 / 中性 / 幽默；正式度 = 随意 / 正式；纠错倾向 = 仅按需 / 温和复述 / 不纠错）。**难度不在用户选项内**——难度由 Ability 层自动驱动（见 §3.9），不暴露「陪练强度」选项。
- 这些偏好由系统**映射为受控片段嵌入提示词**，绝不把用户自由文本原样拼进 system prompt，以避免输入错误或 prompt 注入损坏人设 / 越权（与既有 AI-17 prompt 加固一致，见 §6.6）。
- 若未来确需开放少量自由文本（如昵称），必须经分隔符包裹 + 长度 / 字符校验，且不得进入指令位。
- **v2 新增：Style 层受控片段**（见 §3.11）：当 Learner Model Style 层积累足够数据后，自动派生用户表达风格摘要（如「简洁、偶有幽默」）作为额外受控片段注入；v1 此项为空，不影响基础功能。

### 3.4 对话中的纠错行为（拟真，不打断）
- **默认不内联纠错**：真人朋友不会逐句改你语法；纠错只在用户**长按主动索取**时出现（见 §3.5）。
- **模糊输入的拟真回应**：当用户输入错误过多、影响理解时，语伴应像真人一样**确认 / 二次询问**（「你是想说……吗？」），或给出**调侃 / 玩笑**等自然回应，而不是冷冰冰地报错或强行纠正。该行为写入人设 Prompt。
- **温和复述纠正（gentle recast，可选中间档）**：除「长按显式纠错」与「完全不纠错」两极外，提供中间档——语伴在自己的回复里**自然地用正确说法复述**用户刚说错的内容，不打断、不说教（语言教学公认的高效方式，如用户说 "I goed there" 语伴回 "Oh you went there? ..."）。是否启用可作人设选项（见 §3.3），默认值待定（见 §9）。
- **鼓励优先**：纠错与调侃都以不挫伤信心为前提。上面的「调侃 / 玩笑」必须克制，默认偏向友好确认，避免让缺乏安全感的初学者感到被嘲笑或敷衍（分寸阈值见 §9）。
- **始终目标语言回复**：无论用户用母语还是目标语发言，语伴**听懂后一律用当前语言空间目标语言回复**。注意与 §3.5 的「路由分发」区分——主回复永远是目标语言，路由只决定长按操作的类型。

### 3.5 长按文本操作与语种识别
- **长按 AI 输出的文本** → 翻译 / 语法解析 / **提示（怎么回应）** 等。
  - **「提示」按钮（回应脚手架的具体落地，见 §3.10）**：长按语伴某条消息后出现「提示」操作，点击针对**这条消息 / 这个问题**给出回应建议——用**用户源语言**说明可以怎么答，并给出可直接用的**目标语句型 / 关键单词**。把「不知道怎么开口」就地转成「照着说一句」，直接服务自由产出。
- **长按用户自己的文本**：
  - 若是**母语** → 给出对应的**目标语言表达**（「这句用目标语怎么说」，学习地道表达）。
  - 若是**目标语言** → 检查语法 / 词汇等错误，给出**优化版 / 更自然版**。
- **语种识别策略（两层）**：
  1. **优先本地**：用 Apple `NaturalLanguage` 框架本机判定母语 vs 目标语，快且不外发。
  2. **回退 AI 判定**：若本地识别效果不佳，则在该次请求的系统提示词中写入「用户当前目标语言 = X、源语言 = Y」，并做路由分发——「若文本为目标语言则做纠错 / 优化，若为源语言则做翻译」，由模型自行判定并执行。
- **混合语言 / 夹码输入**：真实学习者常在一句里混用母语和目标语（想说但不会的词用母语顶替）。两层识别不应假设「整条非此即彼」——长按操作要能处理夹码（按主导语言或按选中片段判定）；主对话则把母语片段当作「求助填空」，语伴自然补出目标语说法并继续对话（即一种脚手架，见 §3.10）。
- 设计澄清：路由分发只用于**长按操作的行为选择**，不改变 §3.4「主回复永远用目标语言」的规则。

### 3.6 读取记录、寻找话题（隐私敏感，A+B 兼容）
- 方案 A（用户显式带入）：从记录详情等位置「和语伴聊这条」，仅发送该条内容。
- 方案 B（一次性授权 + 范围限定）：设置中开启「允许语伴参考记录主动找话题」，并可限定时间窗、排除「私密」等标签、排除照片原图等。
- **本地预筛 + 最小发送**：「挑哪条记录聊」尽量在本机用 FTS（后续可接向量检索）完成候选筛选，只把最终选中的内容送往 Provider，而非把整个记录库灌给模型。

### 3.7 朗读与语音输入
- **朗读（初版必需）**：语伴回复复用既有逐句 TTS 朗读基础设施（TTS Provider、artifact 缓存、播放 coordinator 均已落地），强化「语言陪练」体验。鉴于朗读基础设施已完成，**列为初版必需**而非可选增量。
- **语音输入 / 语音对话（远期规划）**：语音对话依赖尚未实现的 Speech Recognition；初版**文本优先**，语音留作远期。
  - **备忘录要求**：依据本文件拆分 active plan 时，必须把「语伴语音输入 / 语音对话」作为跨任务扩展提醒写入 `docs/architecture/notes/`（架构开发备忘录），说明当前文本对话设计需为后续语音能力预留 message schema、输入栏交互与 Speech 权限边界，避免初版设计阻断远期语音。

### 3.8 聊天内容反哺学习（词汇 / 表达提取到记忆库）
- **保持「自动提取」与现有机制一致**：已实地确认——现有记忆候选（`LearningMemoryCandidate`：词 / 短语 / 句型 / 语法点 / 错误模式）是**学习材料分析时由 AI 一次性自动产出**，并在保存分析结果时自动写入 `memory_candidates` 表（`GRDBLearningContentRepository`），**无需用户逐个挑词**；触发点是用户显式的「生成 / 重新分析」，但提取本身是自动副产物。
- 因此聊天提取**也应保持自动**：每轮对话（或 §3.12 对话小结时）自动走**同一套候选产出 + 入库管线**，复用现有 `memory_candidates` 路径与 plan 10/11 记忆系统，而非新造手动选词流程。词汇提取宜每轮进行（成本低）；Memory 生活事实提取建议在 session 结束或手动小结时进行（成本高、质量要求高，见 §3.12）。
- **用户目标语输入 → Ability 产出证据**：用户每轮目标语发言（见 §3.5 语种识别路由判定为目标语的部分）应同步通过**分析账本（intake ledger）**回流至 Learner Model Ability 层，作为产出维度证据（见 [`01-learner-model.md`](01-learner-model.md) §14 / [`02-dynamic-proficiency-assessment.md`](02-dynamic-proficiency-assessment.md) §13.4）。**语伴将成为 Ability 产出信号的主要来源**——这是评估与语伴的双向协同关系，不止「评估→语伴」的单向依赖（02 §13.4）。
- **长按手动加入仅作补充入口**：在自动候选之外，允许用户长按某条消息 / 选中片段手动加入记忆库，覆盖 AI 漏提的情况。
- 现状（2026-06-26 更新）：「存入记忆库 / 复习队列」（plan 10/11 = E7 deposit + E8 复习）已落地；**语伴聊天候选批量 deposit 进复习系统已打通（LM03-S3b-2「对话小结」）**——提取结果区「全部加入记忆库」一键批量 deposit（复用 E7 幂等、纯本地、无新外发），把对话闭合回「记录 → 对话 → 记忆」，见 `plans/done/2026-06-26-feature-lm03-s3b2-companion-session-deposit.md`。
- 让对话不止于聊天，而是持续沉淀为可复习的学习材料，契合 "用生活记录学习语言"——记录、阅读、对话都成为记忆来源。

### 3.9 难度自适应（三层隐式自适应模型，取代手动「陪练强度」）

> **2026-06-15 定稿**：移除「陪练强度」显式用户选项，改为三层隐式自适应。理由：① 该选项是 Ability 层尚未落地时的临时占位补丁，现 01/02 Ability 层已设计完成，补丁功成身退；② 与「真人感」目标直接矛盾——真实语伴不要求对方选难度档位；③ Ability 层校准信号比用户主观选择更准确（02 §2.2）；④ 既有架构备忘录（2026-05-25 §1）已明确「学习难度」是语伴稳定人格属性，由语言空间学习偏好（即 Ability 层）驱动，不通过开放选项设置。

**三层自适应模型**：

- **基线层（Ability 驱动，会话前设定）**：每次会话开始时，从 `LearnerContextProvider` 取 Ability 信号，写入 system prompt 受控片段（如「用户目标语水平约 B1，请使用自然流畅的日常表达」）：
  - **v1**：`LearnerContextProvider` Ability band 未就绪前，回退到 onboarding 静态 `LanguageLevel`（行为与现在完全一致，无需额外选项）
  - **v2**：接入 Ability 动态 band 信号（对齐 02 §14 band 重估落地节点）

- **响应层（会话内实时信号，每轮自然适配）**：通过 persona 指令让语伴像真人一样读信号并调整，**不宣布「我在调整难度」**：
  > 「当用户回复简短或出错较多时，自然放慢节奏、简化句式，必要时给出关怀性确认；当用户表达流畅时，自然引入略高一档的词汇和句型。直接做，不说。」
  这是 i+1 的真实落地：不是「一次性设定水平」，而是「每轮读信号」，与真实语伴行为一致。

- **对话控制层（自然语言，用户主动触发）**：用户直接在对话中表达需求（「speak slower please」「说简单点」「今天挑战一下」），语伴像真人一样即时响应。**这是真人感最大的升级点**：通过对话控制语伴，而不是通过设置菜单。

设计依据：可理解输入（i+1）——略高于当前水平最有效。三层模型比单一静态难度选项更精准、更自然，且全程对用户不可见——他们感受到的就是「语伴真的懂我」。

#### 3.9.1 动态水平评估（已升格为独立需求，建议先于语伴实现）
> 本方向已单独沉淀为 [`02-dynamic-proficiency-assessment.md`](02-dynamic-proficiency-assessment.md)，并建议**排在语伴之前**实现（语伴难度自适应依赖它提供的水平信号）。以下保留要点摘要，细节以该文件为准。

- **问题**：当前只有首次启动的一次性**水平自评 `LanguageLevel`**——主观、静态、易过期。仅凭它驱动难度自适应，长期会失真（用户进步了或当初评高 / 评低）。
- **设想**：设计一个**内部、本地**的「持续水平评估」机制，依据用户的真实语料（语伴对话输入、记录文本、练习表现、记忆候选难度分布等）**周期性或在累计一定素材后动态重估**目标语水平，输出一个比单一 level 更细的画像（如已掌握 / 待巩固词汇与语法点、估算 CEFR 区间、近期趋势）。
- **价值**：不只服务语伴难度自适应，还能反哺学习材料生成难度、练习选材、记忆复习排序、进步可见（§3.12）。
- **边界与定位（重要）**：
  - 这是**跨功能能力**，本质上**超出语伴单一功能范围**——它影响整个 App 的难度与选材体系，不应只作为语伴的内部实现。
  - 因此建议**不在语伴 plan 内顺手实现**，而是按 CLAUDE.md 1.2 / 第 8 条沉淀为**架构开发备忘录**（`docs/architecture/notes/`），评估其是否升格为独立 spec / ADR；语伴初版先用「静态 `LanguageLevel` 作为 Ability 基线」（见 §3.9 三层模型 v1 降级），预留 `LearnerContextProvider` 接口位等动态评估 v2 接入。
  - 必须本地优先：评估在本机进行，输入语料默认不外发；若某步需 Provider，遵循 §6 隐私边界。
- **待决**：评估触发节奏（定期 vs 累计阈值）、输出画像的数据模型、是否向用户透出（避免打击信心）、与自评 level 的关系（覆盖 / 并存 / 仅建议）——见 §9。

### 3.10 冷启动、对话引导与脚手架
- **空会话问题**：首次进入是空白聊天框，对学习者（尤其初学者）「用外语先开口」心理门槛很高。语伴应**主动开口**先打招呼并抛出 1~2 个轻量话题，营造「真人先搭话」的体感。
  - 隐私澄清：这是 App 内**本地发起的首条问候**，不等于「未经授权主动外发用户敏感记录」，§3.6 的隐私边界仍然成立。
- **回应脚手架 = 长按「提示」按钮（按需触发，首选形态）**：不做常驻 chip，而是把脚手架做成**用户主动触发**的操作——长按语伴某条消息 → 点「提示」→ 针对该问题给出**源语言回应思路 + 目标语句型 / 关键词**（详见 §3.5）。
  - 好处：按需出现、不干扰已能独立表达的用户、不抢占聊天界面、与现有长按操作体系统一。
  - 可保留「常驻建议 chip」作为可选的更激进引导（面向纯初学者），默认走长按「提示」。是否默认开启、能否关闭见 §9。
- **空记录场景**：新用户尚无记录时，语伴差异化（「了解你生活」）暂无素材，应优雅退化为通用轻量话题，并引导用户先去记录——这也说明语伴价值随记录积累而增长（见 §4.4、§8 时机）。

### 3.11 长期关系记忆（「记得你」）
> 本能力对应上位文档 [`01-learner-model.md`](01-learner-model.md) 的 **Memory 层**：该模型已于 2026-06-14 第 3 轮重构为 **Ability / Memory / Style 三层 + 系统级（跨语言空间）**（取代旧「关系记忆 / 能力画像两平级子域」，见 01 §13）。关系记忆按层归 Memory，并进一步定为：**生活事实 / 目标升系统级（全局共享、跨空间复用）**、**对话情景留 per-space**。语伴落地时，记忆应填入该统一模块边界，并通过 `LearnerContextProvider` 取用，而非语伴自建 store。以下保留语伴视角要点。

- 差异化不止「读取记录」，还在于语伴**记得你在对话中告诉过它的事**（宠物名、在学什么技能、上次聊到哪）。真人朋友会记得，这是「对象感」的关键。
- 实现上由 §5.2 的「滚动摘要 / 对话记忆」承载，但应在产品上**明确为一项体验承诺**，而不仅是上下文压缩的副产品。
- **删除语义（2026-06-15 修正，对齐 01 §13.3）**：旧表述「清空一并清除关系记忆」与三层模型冲突，现更新为：
  - **「清空对话历史 / 重新开始」** → 仅清对话消息 + per-space `CompanionMemorySummary`（对话情景）；**系统级生活事实 / 目标（Memory 系统层）不随此操作删除**
  - **系统级全清** → 只有「重置 App 对我的了解」（统一治理入口）才清系统级内容
  - **UI 透明提示**：清空时附一行说明：「对话记录已清空。从对话中了解到的关于你的信息仍然保留，可在[学习画像]中查看或删除。」
  - 理由：系统级生活事实的价值恰在于跨越单次对话持续存在；删对话≠让 App 忘记这个人
- **`LearnerContextProvider` 接口契约（语伴视角）**：语伴每次会话开启时，通过 `LearnerContextProvider` 查询以下层，**不自建语伴专属 store**：
  - v1 起必须：Ability 信号（难度基线，见 §3.9）
  - v1 起必须：Memory per-space 对话情景摘要（`CompanionMemorySummary`，「记得你上次说的」）
  - v1 起，按 salience 取前 5 条：Memory 系统级生活事实（上限约束，无 FTS 时的合理降级；v2 接 plan 12 FTS 后改为相关性召回）
  - v2：Style 层受控片段（写作风格摘要，外发受决策 #10 + plan 09 约束，见 §6.9）
  若某层尚未就绪，退化到下级信号，不阻塞语伴功能。
- **Style 集成（v1/v2 分阶）**：
  - v1：Style 层尚无数据，语伴响应风格仅靠 persona 固定模板
  - v2：`LearnerContextProvider` 返回 Style 受控片段，语伴自然融入用户表达习惯（简洁/幽默/类比等），同时经 Ability i+1 下投影（01 §13.5）——不把母语丰富度强加给初学者；「提示」按钮的建议句型也随之个性化
    - **→ surface v1 已落地（LM03-S4a，2026-06-27）**：`CompanionStyleProjection` 把 LM02-S2 surface Style 印记（句长/词汇丰富度/正式度）+ 只读 band 量化为 `CompanionStyleDescriptor`，经 `CompanionPromptRegistry` 注入 `<<<STYLE>>>` 块——正式度镜像语域、复杂度按 `band.estimatedLevel` 只读封顶兑现 i+1；复用 S2b-1 两层 consent（Memory+Style 一闸）、Style 块零原始内容无需 scrub、无新 migration/capability/外发类目。认知风格 v2（AI 校准）仍后置。
- 隐私：关系记忆属高敏感个人数据，默认 local-only、可查看、可删除（统一治理入口）；Memory 生活事实纳入导出 + 可恢复备份（01 §13.7）。

### 3.12 对话小结与进步可见
> **v1 已落地（LM03-S3b-2，2026-06-26）**：小结 v1 = **复用 S2a 提取（含典型错误 errorPattern）+ 候选批量 deposit 进 E7/E8 复习系统**（提取结果区「全部加入记忆库」+ 逐条「已加入」态），把对话闭合回「记录 → 对话 → 记忆」。**不新增摘要叙述 AI**（用户决策）；触发 = 手动（语伴单线程无明确 session 边界，会话结束自动触发 defer）。
- 对话若聊完即逝，学习沉淀为零。可提供**轻量「本次对话小结」**：用到的新词 / 表达、出现的典型错误、可加入记忆库的候选——把对话闭合回「记录 → 对话 → 记忆」。
- 与 §3.8 词汇提取、plan 10/11 记忆系统打通；小结可作为记忆 deposit 的批量入口。
- 让资深用户「看得见进步」，提升留存；触发形态（每次结束 / 手动生成 / 阶段汇总）待定，见 §9。

## 4. 必要性

### 4.1 补齐唯一缺失的练习模态
现有四种练习（跟读、听写、回译、写作修改）**全是「再现 / 转换已有文本」**，唯独缺「自由产出 = 用自己的话互动表达」。对话是语言习得中最难、收益最高的技能，是真实的能力空白。

### 4.2 竞争力（用户主张）
AI 对话几乎是主流 AI 语言学习工具的基础能力，缺失会让产品在用户认知上「少一块」，削弱竞争力。

### 4.3 差异化
「和一个**了解你生活记录**的对象用目标语言聊天」是通用聊天机器人做不出的体验，是 "用生活记录学习语言" 的自然延伸；再叠加「聊天反哺记忆库」，形成「记录 → 对话 → 记忆」的学习闭环。

### 4.4 价值随记录积累增长（对时机的含义）
语伴的差异化建立在「有记录可聊」之上：新用户记录为空时价值有限（见 §3.10 空记录退化）。这意味着语伴更适合在用户已积累一定记录后凸显价值，也佐证了「先做记录闭环、语伴靠后」的排序（见 §8）。

## 5. 复用 vs 新增工作（可行性）

已实地确认：现有 AI 请求已是 `messages:[{role:system},{role:user}]`（Chat Completions 兼容）与 `input` 数组（Responses API）格式，**具备多轮对话底子**；但当前都是「system+user 单发」，无会话历史、无文本流式输出（streaming 目前仅用于 TTS）。

### 5.1 高复用（已有 / 已规划）
- 长按 AI 文本 → 翻译 / 语法解析：近似 plan 05「阅读体验」的 selection-explanation 服务，可复用 Prompt 基础设施。
- 长按用户文本（目标语）→ 检查 / 优化：即产品愿景中已有的「写作修改」能力。
- 长按用户文本（母语）→ 译为目标语：轻量「这句怎么说」服务。
- 词汇 / 表达提取到记忆库：复用 plan 10/11 记忆系统的 deposit 路径。
- 语伴朗读：复用逐句 TTS。
- 请求预览 / 日志：plan 09（AI 请求预览与日志基础）正好覆盖，语伴每次请求都应走这条隐私边界。

### 5.2 真实新增工作
- **多轮对话编排** + **上下文窗口管理**：单一长会话会无限增长撑爆 context，需「滚动窗口 + 摘要（对话记忆）」策略，可与 plan 10/11 记忆系统打通；并需处理「删除某条及其后续」时的摘要失效重建。
- **会话 GRDB schema**：消息表（角色、时间、每条的学习标注缓存、源/目标语言判定结果），默认 local-only、默认不同步、可导出、可按条（及后续）/整段删除。
- **三端聊天 UI**（iPhone / iPad / Mac）：工作量大头（遵循导航 spec 002 与 `docs/workflows/add-platform-screen.md`）。
- **设置开关（默认关闭）+ 菜单项 + 人设选项面板**。
- **人设 / system prompt 模板 + 选项映射层**：新 Prompt Registry 条目；选项→受控片段的映射；声明隐私边界（哪些用户数据会进 prompt）。
- **文本流式输出**（决定「真人感」）：现有 AI-11「响应流式化」已推迟到 plan 01（E0a）；可作为可推迟增量，待基础设施完善后再做。
- **主动找话题的检索**：依赖 plan 12（FTS），理想后续接向量检索。
- **语种识别**：本地 `NaturalLanguage` 接入 + AI 路由回退（提示词内目标/源语言说明与分发逻辑）。

## 6. 与核心决策的关系（实施前必须处理）

1. **定位冲突 → 必须新增 / 更新 ADR**：`CLAUDE.md` 第 3 节明确「产品不是 AI 聊天工具」。本需求改变该定位，必须以 ADR 写明：语伴是「扎根记录的语言对话练习模态」，并列清其与「通用助手」的硬边界（始终目标语言、话题源于记录、以学习纠错为目的、单一对话对象、不承接通用任务）。同时同步更新 `product-main-reference.md` 与入口文档相关表述。
2. **隐私核心决策 #10（明示触发才发送敏感内容）**：原始「主动读取记录」若无授权即自动外发会违反 #10 与 ADR-005。已通过方案 A + 方案 B（显式带入 / 一次性范围授权 + 本地预筛最小发送）化解，实施时必须严格落地。
3. **Provider 抽象（#8）**：对话是新的 Provider 能力，必须走 Provider 抽象；需确认各 adapter 多轮 / 流式支持。
4. **本地优先（#11 / ADR-005）**：会话历史属高敏感个人数据，默认 local-only、默认不同步、可导出、可删除。
5. **成本**：买断制 + 用户自带 Provider，长对话消耗用户自己的 token（对 App 经济无害），但建议 UI 适当透出用量。
6. **Prompt 注入 / 提示词完整性（呼应既有 AI-17）**：用户可调部分**优先选项化**，自由文本（若有）必须分隔符包裹 + 校验，绝不进入指令位；防止用户输入污染人设或越权为通用助手。
7. **在线依赖与失败态**：聊天 UI 天然让用户期待「随时可答」，但语伴本质依赖在线 Provider，与 App 的本地优先气质存在张力。必须设计优雅的失败态（Provider 不可用 / 限流 / 离线）：明确提示「语伴暂时联系不上」、可重试、**不丢用户已输入内容**、不伪装成正常回复。
8. **成本可见与失控防护**：单一长会话每轮都要重发历史 + 摘要，token 随对话增长而上升、消耗用户自带额度。除 §6.5 透出用量外，建议提供软提示（「对话已较长，是否开启摘要压缩 / 重新开始」），让成本可感可控。
9. **Memory 注入的隐私边界（2026-06-15 新增，2026-06-15 第 6 轮修订）**：每轮对话将 Memory 生活事实受控摘要注入 system prompt 并发给 Provider，属于**系统自动注入**外发行为，受决策 #10 约束（不同于用户打字发送——那属于用户主动触发，不需额外授权）。隐私机制分两层：
   - **全局层（首次开启）**：首次开启语伴时呈现预览「语伴对话中会将你的学习画像摘要（水平 + 记忆要点，v2 后含风格摘要）发给你配置的 AI Provider」（复用 plan 09 请求预览逻辑），提供全局「不使用学习画像」关闭选项；首次确认后不再每次弹出，降低摩擦。
   - **per-conversation 层**：对话顶部信息栏或设置入口提供「本次对话不使用学习画像」快捷开关，让用户可灵活控制单次对话是否携带 Memory，无需进入设置；偏好在会话级记录，不修改全局设置。
   - **PII scrubbing（defense-in-depth）**：注入内容和用户消息在发给 Provider 前，对结构化 PII（手机号、身份证号）做确定性 scrubbing；不替代上述授权机制，作为补充保护。
   不为每类信号单独设 opt-in（与语伴功能整体 opt-in 合并处理），但两层控制确保用户随时可感知、随时可关闭。

## 7. 大致实施路线（建议分期，待拆为正式 plan）

> 以下为方向性路线，非承诺；正式拆解时按依赖关系排序，并各自走 plan + 自审核 + 用户确认。

- **第 0 步（前置，定位）**：新增 / 更新 ADR 确认语伴定位与边界；更新产品主参考与入口文档。
- **第 1 步（地基依赖）**：确保 plan 09（AI 请求预览 / 日志）已落地；确认 Provider adapter 多轮 / 流式能力（可能牵动 plan 01 / E0a 流式化）。
- **第 2 步（最小可用 MVP）**：
  - 设置开关（默认关闭）+ 三端入口 + 基础人设选项；单一会话纯文本对话（多轮编排 + 上下文窗口管理）。
  - 始终目标语言回复；模糊输入拟真确认 / 调侃；会话 GRDB schema（local-only、可按条及后续 / 整段删除）。
  - 长按操作：翻译 / 语法解析 / **「提示」回应脚手架**；复用阅读解释 / 写作修改 / 轻量翻译服务；语种识别先做本地，必要时叠加 AI 路由回退。
  - 话题来源先只做**方案 A（用户显式带入单条记录）**。
  - **语伴朗读（初版必需，复用既有 TTS）**。
  - 难度自适应：初版用三层自适应模型（§3.9），基线层 v1 回退静态 `LanguageLevel`；**无「陪练强度」选项**；动态水平评估暂不在此实现（见 §3.9.1 备忘录）。
  - 词汇 / 表达提取到记忆库：**自动产出 + 入库**对齐现有 `memory_candidates` 机制（落地节奏对齐 plan 10/11）。
- **第 3 步（增量）**：

## 10. 架构师评审（2026-06-13，基于代码与既有备忘录实地核对）

> 已核对：当前 AI 请求确为 `messages:[system,user]` **单发、无多轮、无文本流式**（仅 TTS 走流式）；`LearningMaterialGenerationService` 仅支持 OpenAI-compatible chat 与 Responses，**Anthropic / Gemini 明确不支持**；plan 09 请求预览 / 日志**尚未实现**（`RequestPreviewCard` 仍是 mock，全仓无 `ai_request_log` 基础设施）；逐句 TTS 播放协调器（`SentenceAudioPlaybackCoordinator` 等）已落地可复用。跨文件结论见 [`README.md`](README.md) §6。

### 10.1 必须先归并既有架构备忘录（最高优先，本构想此前漏检）
仓库已存在 `docs/architecture/notes/2026-05-25-language-companion-extension-notes.md`（Accepted），本构想（2026-06-13）**未引用它**，且在三处分歧，拆 plan 前必须对齐：
1. **入口位置**：备忘录明确「**不建议**第一阶段把语伴做成与记录 / 练习 / 记忆并列的第四个底部 Tab」，推荐做练习 Tab 内二级入口、或 Entry「围绕这条记录对话」入口；本构想 §3.1「三端导航 / 菜单栏新增语伴入口」措辞偏向顶层。**需对齐**。
2. **数据模型命名**：备忘录已给出 `ConversationCompanion / CompanionThread / CompanionMessage / CompanionMemorySummary / CompanionAnalysis`；本构想用泛化「会话表 / 消息表」。拆 plan 时应**复用备忘录命名**，避免二次造名。
3. **记忆归属**：备忘录把对话记忆定义为语伴作用域 `CompanionMemorySummary`；idea 01 要升格为跨 App 记忆。见 [`01-learner-model.md`](01-learner-model.md) §12.5 的 `scope` 分层折中（物理统一存储、默认 `companionOnly` 可见）；2026-06-14 第 3 轮进一步定为 **Memory 层**：**生活事实升系统级**、**对话情景留 per-space**（见 01 §13.2）——备忘录的纯 per-space 记忆假设需据此再对齐。
- **行动**：拆 active plan 前按 `notes/README` §5 读取该备忘录并在 plan 中说明采纳 / 分歧处理；建议本构想与该备忘录**显式互链**。

### 10.2 ROI 与排序：语伴是三者中 ROI 最差、依赖最长，应排最后
诚实评估：语伴建设成本最高（多轮编排 + 上下文预算 + 文本流式 + 三端聊天 UI + 人设选项 + 失败态），隐私治理负担最重，且本质是 **me-too**（人人都有聊天）；其差异化（扎根记录 + 关系记忆）**完全依赖**记录语料、关系记忆、FTS 找话题三者都先成熟——**价值后置**。
- **更优 de-risking（建议正式评估）**：语伴的多数**学习价值**——长按「提示」回应脚手架、「这句目标语怎么说」、目标语写作纠错——本质是**已规划的阅读 / 写作服务的会话化呈现**。可先把这些做成现有界面上的**会话式 affordance**，交付约 80% 学习价值而**不建**完整聊天引擎。完整语伴（单线程多轮 + 流式 + 关系记忆）作为其后增量。这把「最贵的一块」从关键路径摘下。

### 10.3 流式与 Provider 抽象的依赖链比 §5.2 所述更长
- 文本流式当前**不存在**（仅 TTS），且 AI-11「响应流式化」已推迟进 **plan 01（E0a）**；语伴「真人感」高度依赖流式，故其体验质量被 E0a 流式项是否落地**门控**。
- 当前生成服务**不支持 Anthropic / Gemini**；一个**聊天**功能现实上需要 Anthropic Messages API（多轮 + 流式一等公民）。语伴会**倒逼 Provider 抽象扩容**到多轮 + 流式 + 多家适配。建议在 plan 中把「Provider 抽象多轮 + 流式 + Anthropic 适配」列为**显式前置**，而非隐含进 MVP。
  - **→ 已落地**：多轮 + 文本流式 enabler（OpenAI 兼容族，2026-06-25）+ **Anthropic Messages 多轮+流式适配（LM03-S4b，2026-06-27，全量 CI 绿 run 28252751284）**——`AnthropicMessagesTextAdapter`（顶层 system / 必填 max_tokens / `content[].text` / `content_block_delta` 流式 / 无 `[DONE]` EOF 终止）+ 鉴权可动态派发协议要求 `providerRequestHeaders`（连带修复 mimo 潜伏鉴权 bug）。语伴 send 路径 kind-agnostic、零 App 改动即可跑 Anthropic。Gemini 仍后置。

### 10.4 在线依赖与本地优先气质的张力（§6.7 已触及，补充产品落点）
聊天 UI 让用户期待「随时秒回」，但语伴本质依赖在线 Provider，与本地优先气质冲突最大。除失败态外，建议在产品层**主动降低秒回期待**：把它定位为「**练习对象**」而非「**助手**」——UI 文案、节奏、朗读优先都强化「这是练习」，避免培养「随叫随到的 AI」预期。
