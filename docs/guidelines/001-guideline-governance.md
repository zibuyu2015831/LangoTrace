# 001：开发规范治理

状态：Accepted

适用阶段：工程初始化前、SwiftUI App Shell、MVP 早期开发。

## 1. 适用范围

本文档规定语迹 LangoTrace 开发规范的治理方式，包括规范的优先级、变更条件、记录方式和 AI 辅助开发时的使用要求。

## 2. 当前结论

开发规范是语迹工程化文档体系中的执行层。它位于主参考文档、技术路线和 ADR 之下，用于约束具体实现风格、模块边界、UI 一致性和 AI 编码行为。

规范不是永久不变的教条。开发过程中如果发现更优设计，可以更新规范；但必须记录原因、影响范围和是否需要 ADR。

## 3. 优先级

当文档之间出现冲突时，按以下优先级判断：

1. 用户当前明确指令。
2. ADR 和主参考文档。
3. 架构文档。
4. 开发规范。
5. 阶段计划和实现细节。
6. 旧聊天记录。

如果规范与 ADR 冲突，不能直接按规范实现，应先更新 ADR 或提出冲突说明。

## 4. 强制规则

- 涉及产品核心模型变化，必须更新产品主参考文档和 ADR。
- 涉及技术路线变化，必须更新技术框架与开发路线参考和 ADR。
- 涉及数据、隐私、同步、AI 请求、密钥、付费和发布边界变化，必须更新对应主文档或 ADR。
- 涉及开发一致性但不改变核心架构的变化，可以只更新 guideline。
- AI 辅助开发时，必须按任务类型读取相关 guideline。
- 如果实现中发现更优方案，不能悄悄偏离规范；应先说明差异，再更新规范或实现。
- 新增 guideline 时，必须把它加入 `docs/guidelines/README.md`，并在需要时更新根目录入口软链接指向的 `docs/README.md`。
- guideline 从 `Accepted` 被替换时，应标记为 `Superseded`，并指向新的文档或 ADR。
- 新功能、bug 修复、架构调整、数据/AI/隐私/同步/权限/付费相关任务，实现前必须先创建 `docs/worklogs/` 工作记录并经用户确认。

## 5. 默认推荐

每份 guideline 建议包含：

- 状态。
- 适用阶段。
- 适用范围。
- 当前结论。
- 强制规则。
- 默认推荐。
- 可演进部分。
- 反例。
- AI 开发提示。
- 变更记录。

### 5.1 状态定义

规范状态含义：

- `Draft`：可讨论草案，不能作为强制开发依据。
- `Accepted`：当前生效规范，后续开发默认遵守。
- `Superseded`：已被新规范或 ADR 替代，保留用于历史回溯。
- `Rejected`：讨论过但不采纳，保留原因。

### 5.2 变更记录格式

变更记录建议使用：

```text
- YYYY-MM-DD：变更摘要。原因：...。影响范围：...。是否需要 ADR：是/否。
```

如果变更影响多个规范，应在每份受影响文档中记录，并在 `docs/README.md` 中更新入口。

## 6. 可演进部分

以下内容通常可以在不新增 ADR 的情况下更新 guideline：

- UI token 命名。
- 组件拆分粒度。
- 页面内布局细节。
- ViewModel 命名。
- Mock 数据组织方式。
- 阶段性验证命令。

以下内容通常需要 ADR：

- 放弃 SwiftUI Multiplatform。
- 从语言空间改为 Project。
- 从本地优先改为云端优先。
- 从用户自带 Provider 改为官方单一 AI 服务。
- 从 SQLite / GRDB 长期候选改为 SwiftData-only。
- 将 API Key 或同步密钥默认纳入同步。

## 7. 反例

不应这样做：

- 因为某个页面实现方便，就绕开 Provider 直接发 AI 请求。
- 因为某个 View 需要数据，就在 View 中直接访问 SQLite 或 Keychain。
- 因为某个原型看起来好看，就引入和 UI 规范冲突的大面积样式。
- 因为当前会话没有读取旧文档，就重新定义语言空间、导航或同步模型。

## 8. AI 开发提示

AI 在开始开发前应先判断任务类型：

- 功能、bug、重构、调研、工程杂项：先判断是否需要创建 worklog。
- 导航、页面、信息架构：读取导航与路由规范。
- 视觉、布局、组件：读取 UI 设计系统规范。
- SwiftUI 代码组织：读取 SwiftUI 架构规范。
- AI、Prompt、TTS、OCR、请求预览：读取 AI Provider、Prompt 与隐私规范。

如果任务跨多个规范，应同时读取相关规范，不应只读其中一份。

完成涉及规范的开发前，AI 应检查：

- 是否已创建必要的 worklog，且状态已经从 `Draft` 进入 `User Approved`。
- 是否引入了新的导航模式、状态对象、服务调用方式或 UI 风格。
- 是否与当前 guideline、ADR 或主参考文档冲突。
- 是否需要补充 guideline、架构文档或 ADR。
- 是否需要把新增规范入口写回 `docs/README.md`。
